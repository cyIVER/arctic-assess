# Independent DVWA installer review

**HOLD before cloud activation.** The source is digest-pinned, but the deliberately vulnerable web container would join the shared ARTEX app/PG/sink bridge without traffic policy. No live launch was performed.

## Blocking findings
- **HIGH F1 — Deliberately vulnerable web joins shared ARTEX data plane with no east-west ACL** (`install.py:19`). The DVWA web container shares 172.29.88.0/24 with ARTEX app, PostgreSQL (172.29.88.2), and sink (172.29.88.4). Same-bridge ports are reachable by default; the alias does not restrict traffic. A DVWA RCE/SSRF exercise can target non-lab containers, and shared app/sink may reach vulnerable web. The backend DB is separate, but web is not constrained to only it and ARTEX ingress. No actual attack or reachability probe was performed. **Action:** Before launch use a dedicated lab network plus a narrowly policy-enforced app-to-target ingress/proxy, or verified host firewall rules restricting DVWA web to its DB and approved ingress only; test denial to ARTEX PG/app/sink and allow intended paths, including teardown. Do not attach vulnerable web directly to the app data-plane network.
- **HIGH F2 — Internal bridges do not prove host-management isolation** (`install.py:69-70`). Existing internal bridge has host gateway 172.29.88.1; new backend internal bridge uses default gateway mode. Docker documents that internal bridges normally have host-accessible bridge addresses and containers can reach host listeners there or on wildcard addresses. No host INPUT restrictions or guest-level denial test exists, so host management surfaces cannot be called confined. Internet egress is restricted by internal networking under default rules, but DNS forwarding/host route policies were not observed. **Action:** Verify host listeners and firewall/bridge gateway mode; enforce and test deny from both web and DB to gateway and management addresses, while retaining allowed lab DB and ingress. Do not infer host isolation from Internal=true.
- **MEDIUM F3 — Real startup and inherited image filesystem compatibility remain untested** (`install.py:43-56`). Image config confirms default root entrypoints, not compatibility of nonroot Apache/MariaDB initialization with read-only root, noexec tmpfs, and dropped capabilities. MariaDB entrypoint creates datadir and initializes a temporary server; Apache must bind port 80 and write logs/runtime/session files. No image layers or daemon launch were examined; no proven startup failure, but readiness is unknown. **Action:** In separately approved confined guest, retain exact run args; collect owned container logs and inspect results, verify temporary initialization, Apache HTTP/session and DB setup; stop/fail closed on error rather than relax guards.
- **MEDIUM F4 — Authentication and seed checks do not prove the requested vulnerable SQLi path** (`install.py:110-125`). The health gate posts setup, verifies seed counts, and authenticates but never requests /vulnerabilities/sqli/?id=...&Submit=Submit or checks security=low in session. Low-level source interpolates id into SQL, but image/source build identity is unproved and a real HTTP finding has not been shown. **Action:** Within freshly created lab DB after confinement, GET a baseline id and a non-destructive comparison payload, require a changed response and explicit low security cookie/session; record HTTP response evidence without mutating non-lab resources.
- **MEDIUM F5 — Digest integrity is not source-build provenance** (`pins.json:3-11`). Manifest and config digests match registry metadata, but OCI labels give only mutable source repository URL, not a build commit/attestation. The independently fetched current source commit is not demonstrated to be the content in the pinned image. No image-layer contents, SBOM, signature or vulnerability scan were reviewed. **Action:** Bind reviewed image to a verifiable source revision/build attestation or explicitly accept this provenance gap; do not claim source/image equivalence. Check unpacked disk and image scan before acquisition as required.
- **LOW F6 — Disposable credentials exposed in process command line and Docker inspect** (`install.py:49-55`). Lab-only passwords are in docker run/exec argv and environment, visible in process inspection/log tooling to authorized guest operators. Not operator credentials, but avoid carrying them to other environments. **Action:** Keep disposable and bounded to this lab; avoid publishing logs/argv and rotate if scope changes.
