## Blocking findings

1. **HIGH — unauthenticated guest-listener starvation** (`guest_gateway.py:52-55`, `bridge.py:193-207`). `HTTPServer` serves one connection at a time; `BaseHTTPRequestHandler` cannot inspect Authorization until it finishes incoming headers. A peer routable to `172.29.88.1:18761` can hold a partial header for up to the 60-second per-request deadline, then repeat without knowing the task key, blocking authorized ARTEX requests. This is source-proven conditional on reachability, **not** an observed DVWA route. Fix by source-restricting the interface at network/firewall boundary to the intended ARTEX peer, denying DVWA and all other guests, and bounding unauthenticated header occupancy independently (e.g. concurrent isolated handlers plus short header deadline); retest with fake slow-header IO before live use. If only one guest is routable, prove it explicitly rather than treating bearer auth as connection admission.
2. **BLOCKING DEPLOYMENT GATE — source/key confinement unproven** (`guest_gateway.py:48-53`). Binding the host-only address and comparing a bearer key are not proof DVWA cannot route there or obtain the key from guest filesystem/container mounts. Parent must verify actual routes, firewall/namespace and key-file ownership/mount isolation without exposing key values. No keyless authenticated request bypass was found in source. Parent must prohibit process auto-restart/second session and terminate owned processes by the UTC deadline; process-local budgets do not survive restart.

**MEDIUM compatibility edge:** `bridge.py:110-119,152` recursively rejects `metadata.url` though that is application data (`repro.py:test_nonstandard_metadata_url_is_rejected`). Current Norma request struct does not emit `metadata`; normal ARTEX `tools`/`messages` are exempt and passed. Do **not** relax top-level transport/auth/model restrictions; only adjust recursion if an actually needed application field appears.
